The Federated Compact

Connecticut's entrepreneur support organizations each keep their own systems and their own client relationships — yet entrepreneurs retell their story at every door, referrals vanish into cold emails, and nobody can show the state what the ecosystem achieves together.

This is a working prototype of the federated answer: instead of everyone joining one central registry, each organization keeps its own software and data, and agrees to a small shared compact — a handful of common fields, consent rules the entrepreneur controls, and a way to recognize the same person across systems.

No new UI. No new platform. And the shared list is held in common — jointly governed, no single organization owns it.
Just a small protocol your existing systems already speak — five plain HTTPS calls:

▶ POST /partnerUpsertPerson …an agency's system talks… ◀ HTTP 201 { "ok": true, "action": "created" } …the network answers. The sandbox is online now. Nothing to install — any HTTP tool can call it.

Everything in this deck is running code, open source under MIT — github.com/jrlogan/Entrepreneurship-Nexus — and the live demo at the end runs against a sandbox you can call from your own laptop.

A system asks

An organization's existing software sends a small package of text (JSON) to the shared network node. Nobody types this by hand — it fires automatically when staff save a record.

◀ incoming

The network answers

The reply always says whether it worked and what happened. The numbers are just status shorthand: 200/201 = success, 401/403 = wrong badge, 404 = not found.

The assignment · agreed Aug 7

Two prototypes, one spec

Chris built the centralized model — a shared registry that owns entrepreneur identity. This is the federated answer to the same four steps: every organization keeps its own system, its own data, its own IDs.

  1. A new user registers as an entrepreneur …in a provider's own system — no central signup form
  2. The entrepreneur is linked to service provider A …a dated, typed relationship on the shared record
  3. They link to a second provider B …B's system recognizes the same person: action: "linked"
  4. The entrepreneur works with B while A is offline …no single point of failure, in data or login

The heart of the compact · what everyone signs up to

Always shared · shared by consent · never shared

Always · by the compact

The operational minimum, visible to staff at orgs the entrepreneur actually works with:

  • Name and email (identity core)
  • Each org's own participation & referral records with them
  • Shared tags ("entrepreneur", "patent")
Only with their consent

Off by default; the entrepreneur opts in from an email link:

  • Listing in the cross-org network directory
  • Another org seeing a first org's records — asked per share, or granted upfront to named trusted partners
  • Revocable; data-deletion built in
Never shared

Stays inside the org that wrote it:

  • Internal record IDs (each org sees only its own)
  • Interaction notes (excluded even from webhooks)
  • Financials, custom fields — anything unmapped

Privacy Notice — the entrepreneur signs

"Each ESO only sees records they have created or that you have explicitly shared with them." · "We do not sell your data… notes are confidential between you and the recording organization."

Data Usage Agreement — each org signs

"Access entrepreneur information solely to provide ecosystem support services." Versioned signatures, in-app; both documents are drafts this group edits before v1.0.

Level 2 in practice · integrated into your system

What joining actually looks like, step by step

  1. Get your credentials — an org ID and an API key for your organization. One email. Your key is yours alone; every write is attributable to you.
  2. Map your fields to the compact core — which of your columns is first name, email, venture name. ~1 hour with the mapping worksheet. Your internal record IDs are never translated — they ride along as your external_ref.
  3. Map your taxonomy — your program names onto the shared vocabulary (next slide). The compact fixes ~7 participation types and 4 statuses; everything else stays local.
  4. Wire "push on save" — when staff save a contact or enrollment, your system fires the call you saw in the demo. An afternoon. The AI integration prompt scaffolds this for your stack (PHP, Node, anything that can POST).
  5. Grow organically — no bulk import — each entrepreneur enters the shared network the first time you actually work with them: a saved record, an enrollment, a referral. The consent email goes to that person at that moment. Idempotent calls mean duplicates are impossible as activity accumulates.
  6. Later, if you want — webhooks for real-time referrals; register your login as an identity provider. Both optional, both reversible.

The hard question · "we all spell names differently"

Identity, duplicates, and how they get fixed

Every data-sharing effort dies here. The answer is three separate jobs — avoid, resolve, reverse — and refusing to guess in the middle one.

  1. Avoid — match on things that don't vary Your own record ID first (external_ref), then exact email or domain. Never on spelling. "Bob Smith" vs "Robert Smith Jr." never auto-merges.
  2. Flag — a weak signal is a question, not a decision Similar name + same email domain? The system creates the record so nobody is blocked, and flags the pair for review. The API never silently merges two people.
  3. Resolve — a human decides, in the GUI This is what the interface is for: an admin sees both records side by side and picks the survivor. Most days the API does everything; the screen exists for exactly this.
  4. Reverse — every merge is undoable The merged record is archived and tombstoned, never deleted, recording precisely which IDs moved. Unmerge puts back exactly those and nothing else.

Why nobody loses their pointer

On merge, every partner's ID from the losing record is copied to the survivor and its lookup entry is repointed. An agency that only knows its own ID keeps resolving to the live record — no reconciliation on your side, no broken integration.

The safety properties

  • Merges run in a transaction — no half-merged state.
  • Tombstoned records redirect reads to the survivor.
  • Merge and unmerge are both written to the audit log, with who and when.
  • Only platform admins and ecosystem managers can merge.

Try it in the compact demo: Data Quality shows pending duplicates with a side-by-side review and a survivor choice.

Day to day · the two actions that build the timeline

How a referral happens · how a session gets logged

Sessions & milestones — logged where staff already work

Facts on the timeline, details at home

  • Coaching / mentoring: staff log the meeting in their own CRM as they do today; the system pushes a dated event — type, date, org. Notes never leave the recording org; sharing "it happened" is a per-event choice.
  • Memberships & programs: starts, completions, and lapses flow automatically (active → past, history kept). Outcomes (jobs, revenue) recorded as standard metrics, self-reported or verified.
The day-to-day payoff

Coordinate, don't duplicate

  • Before reaching out about a shared client, staff see who's already helping and how recently — and can call that agency to coordinate.
  • Start at the email level today; integrate later. Every level feeds the same timeline — and the statistics — with no extra reporting work.

The statistics payoff · aggregate & anonymous, by design

What the shared timeline can answer

For the state & funders
  • Entrepreneurs served statewide — deduplicated. Linked identity means a founder helped by four orgs counts once, not four times. That's what makes the number credible.
  • Businesses started, and still operating at 1 / 5 / 10 years — the survival-rate study EF assembled by hand via LinkedIn becomes a query, with national baselines for comparison.
  • Jobs (FT/PT) and revenue — standard metrics, each tagged self_reported or verified, aggregated for the funding case.
  • Retention in Connecticut — where network-supported ventures end up.
For the network & each org
  • Referral flow that closes: volume, acceptance rate, and time-to-first-meeting — by org pair, so bottlenecks are visible.
  • Collaboration measured: how many entrepreneurs are served by 2+ organizations, and which hand-offs actually happen.
  • Program reach: enrollments, completions, and coaching cadence across the ecosystem.
  • Your own view: each org sees its clients' cross-org activity — support better, or call the other agency to coordinate.

All of it is aggregate and anonymous — entrepreneur-level data never leaves the consent rules to produce a statistic. And none of it is extra reporting work: the numbers are a byproduct of referrals, enrollments, and sessions the orgs already record.

  • No single point of failure for the providers — every org's own system stays primary; the shared node syncs, it doesn't gatekeep.
  • Login survives outages too — any org can register its existing sign-in as an identity provider; sessions are minted independently, so entrepreneurs still get in when their home org is down.
  • Entrepreneur consent gates visibility — pushed records stay out of the shared directory until the person opts in by email; data-removal is built in.

Discussion · the group's to-do list

What the group must decide — in order

  1. Ratify the compact — the governance principles: sovereignty, consent, permitted uses. Draft exists as a signable, versioned document.
  2. Fix the common core fields — the small set every org shares. Starting point: data-standards v1.0 (name, email, venture, participation).
  3. Agree the shared taxonomy — participation types, referral statuses, tag conventions. Currently 7 types, 4 statuses — trim or extend.
  4. Set the entrepreneur agreement text — the consent language every org presents. Draft Privacy Notice exists; the group edits it.
  5. Choose the identity approach — which orgs register their sign-in as a provider; email-linking rules for the rest. Entrepreneur Central can be one of them.
  6. Pick the operator — joint council, lead nonprofit, or each org self-hosts and bridges. MIT license keeps every option open — and reversible.
  7. Run a pilot — two orgs integrate against the sandbox, real referrals flow for 30 days, group reviews. Keys and integration packet are ready today.
  8. Define the shared metrics — the aggregate numbers we report to the state: startups, survival, jobs. Falls out of participation records automatically.

Everything shown today is open source under the MIT license — the code, the partner API, the data standard, the agreement drafts, and these slides: github.com/jrlogan/Entrepreneurship-Nexus. Fork it, self-host it, audit it — or let's run it jointly. No one is locked in, including to MakeHaven.
